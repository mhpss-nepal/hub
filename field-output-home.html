Where the field forms' output lands

The field forms run on the phones (Layer 1) and are not repeated here. This is the Layer 2 side of the same thing: the surface that reads what a form wrote. It answers one question with something you can check — a record made on the current field form arrives on Layer 2, through the existing contract, and is read.

Structure only. No visual design is proposed on this page, and none is approved. The layout, typography, colour, card style and navigation shape of the Layer 2 home are Adib's decision and are deliberately not made here. This page exists so the plumbing has an address that can be tested. Anything that would present itself as "the Layer 2 look" is out of scope until he confirms it. The questions he is being asked are listed at the foot of this page.

The receiving surface

This route is the home the forms' output lands in. It reads the register through the same two shared files every Layer 2 screen uses — assets/fb.js (the register bridge) and assets/store.js (the record model) — with neither of them modified. It requests exactly one record kind, activity, which is the instrument approved for the trial; asking for a kind is the read boundary, not a display filter.

What this page does not do

  • It never writes. FB.submit() and FB.publish() are wrapped so an attempt is recorded and refused; the counters above stay at zero.
  • It changes no contract. No field name, no schema, no storage key, no id basis, no queue behaviour, no rule. Both shared files are loaded as they are.
  • It touches no file in the form repository. Layer 1 is frozen; any incompatibility is solved here.
  • It is not a dashboard and proposes no layout. It is the minimum surface that makes the read path testable.
